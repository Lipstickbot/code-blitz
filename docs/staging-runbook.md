# Code Blitz Staging Runbook

## Goal

Staging is the first real server target before production. It should behave like production for safety checks, Redis rate limits and Docker judge isolation, but it can use test data and a temporary domain.

## Files

- `blitzcode-mvp/backend/.env.staging.example`
- `blitzcode-mvp/backend/docker-compose.staging.yml`
- `blitzcode-mvp/backend/Caddyfile.staging`
- `blitzcode-mvp/backend/scripts/check_staging.py`
- `blitzcode-mvp/backend/scripts/deploy_staging.sh`
- root static frontend files: `index.html`, `app.js`, `styles.css`, `config.js`

## First Setup

On the staging server:

```bash
cd blitzcode-mvp/backend
cp .env.staging.example .env.staging
```

Then edit `.env.staging`:

- set `STAGING_DOMAIN` to the staging domain;
- set `ACME_EMAIL` for HTTPS certificate notices;
- replace `JWT_SECRET` with a random value of at least 32 characters;
- replace database password placeholders;
- set `CORS_ORIGINS` to the HTTPS staging origin;
- keep `ENVIRONMENT=staging`;
- keep `AUTO_CREATE_TABLES=false`;
- keep `RATE_LIMITER_BACKEND=redis`;
- keep `JUDGE_EXECUTOR=docker`.

For the full server, DNS and GitHub Actions checklist, use `docs/staging-deployment-checklist.md`.

## Readiness Check

Before deploying, run:

```bash
cd blitzcode-mvp/backend
python scripts/check_staging.py --env-file .env.staging --with-docker
```

The check validates:

- required staging files;
- domain and ACME email;
- database and Redis settings;
- production/staging safety rules;
- Docker Compose staging config.

## Deploy

```bash
cd blitzcode-mvp/backend
bash scripts/deploy_staging.sh
```

The script:

- pulls Python and Node judge images;
- runs staging readiness check;
- builds the backend API image;
- starts PostgreSQL and Redis;
- runs production preflight against `.env.staging`;
- applies Alembic migrations;
- starts the API and Caddy reverse proxy;
- prints service status.

## Frontend/API Routing

Caddy serves the static frontend and proxies backend routes on the same HTTPS domain:

- `/` serves `index.html`;
- `/app.js`, `/styles.css`, `/assets/...` serve static files from the repository root;
- `/config.js` is generated by Caddy for staging and sets same-origin API/WebSocket access;
- `/api/...`, `/docs`, `/openapi.json` proxy to the backend API.

This means the browser calls `https://your-staging-domain.example/api/...` and WebSocket uses `wss://your-staging-domain.example/api/matches/...`.

## Health Check

```bash
curl http://127.0.0.1:8000/api/health
curl http://127.0.0.1:8000/api/health/ready
curl https://your-staging-domain.example/
curl https://your-staging-domain.example/api/health/ready
```

Expected result:

- `status: ok`;
- database is ok;
- rate limiter uses Redis;
- judge executor is Docker.
- HTTPS is served by Caddy.
- frontend loads on the staging domain.

## DNS and Firewall

Before running the deploy script, point the staging domain A record to the server IP.

Open inbound ports:

- `80/tcp` for ACME HTTP challenge and redirect;
- `443/tcp` for HTTPS traffic.

The API container binds `8000` to `127.0.0.1`, so direct backend access stays local to the server. Public traffic should go through Caddy.

## Notes

The staging compose file mounts `/var/run/docker.sock` into the API container so the backend can start isolated judge containers. This is acceptable for the first staging target, but the cleaner production direction is a separate judge worker service or managed judge platform.
